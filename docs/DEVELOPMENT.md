## Private development flow

1. Resolve current `development/jv-web-r1` remote tip/tree.
2. State one narrow technical/product question.
3. Protect the last accepted owner-visible baseline.
4. Change only the declared subsystem.
5. Run focused checks and the smallest relevant runtime smoke.
6. If the claim is visual/feel/device-dependent, prepare a stable candidate and ask Jozz only for that observation.
7. Record an accepted owner-visible checkpoint in `docs/OWNER_CHECKPOINTS.md`.
8. Integrate/fast-forward into `development/jv-web-r1` and clean temporary branches.

PRs are optional. Do not add custom GitHub Actions by default.

## Validation tiers

### Tier 1 — ordinary private slice

Required:

- exact source identity;
- attributable scope;
- focused tests/checks for the changed subsystem;
- relevant type/build validation when those boundaries changed;
- smallest useful browser smoke if runtime behavior changed;
- truthful statement of what was not tested.

### Tier 2 — owner checkpoint

Use for vehicle proportions/placement, camera feel, touch behavior, scan appearance/performance or driving/config usefulness.

Agent performs automatable validation first. Jozz should only need to drive/look/feel and answer a focused question.

### Tier 3 — public release candidate

Required:

- exact source identity;
- reproducible artifact;
- artifact hashes/provenance;
- public promotion verification;
- rollback point;
- live HTTPS smoke;
- owner acceptance appropriate to the release.

## Branch discipline

Long-lived authority is `development/jv-web-r1`. Temporary branches exist only for bounded isolation and should disappear after integration/rejection. Never create per-agent branches.

See `docs/BRANCH_ROLES.md`.

## Before public promotion

Preserve R0. Publish a new versioned R1 artifact rather than rebuilding or modifying `release/r0` in place. Ensure no private scan bytes are included accidentally.
