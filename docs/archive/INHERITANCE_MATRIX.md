This matrix is the current cross-project decision instrument for JV-Web. It supersedes the older donor-intake routing that treated `Front Mechanical Unit 01` as an already-defined first Web stage.

It does **not** select runtime architecture, select the first falsifier, freeze a JURE -> Web lowering format, make JURE mandatory, freeze TypeScript/WASM, freeze the renderer, freeze a universal component ontology, or authorize a runtime substitution.

Authority order:

`live Git/current files -> executed evidence -> direct scoped Owner feedback/device evidence -> current documentation -> historical plans/conversation memory`

Inheritance order:

`Owner product truth -> portable mechanical/semantic truth -> proven recipient/donor technique -> candidate implementation -> legacy defaults/docs`

Primary-donor status never wins a conflict automatically.

## 1. Gate inputs reconciled

### Gate 1 — donor deconstruction

High-confidence donor/cross-project constraints include:

- independent owner-local relation endpoint truth;
- authored/neutral mechanical truth separate from runtime dynamics/contact/solver policy;
- coherent mechanical units rather than mixed incompatible geometry authorities;
- real M6 front roles without an invented additional physical carrier body;
- provenance/deterministic identity and persistence as useful authored-truth requirements;
- physical steering/back-drive intent with artificial rack centering OFF as the default policy;
- mode5 / analytic real-width wheel as the current Owner-selected donor/product direction, but not final tire architecture;
- split sphere+sidewall retained only as stale implementation/control evidence;
- known mode5 large-angle anti-centering preserved as a future falsifier, not a solved defect.

### Gate 2 — JV-Web technology capital / recipient map

The recipient is not uniformly legacy. Strong current Web capital includes:

- product input ownership/lifecycle and multitouch behavior;
- fixed-step/browser presentation separation;
- tracing/telemetry/evidence surfaces;
- `VehicleVisualFrameV1` and useful binding techniques;
- strict world/scan validation and current mobile resource discipline;
- accepted camera/fullscreen/mobile product behavior;
- exact-source Preview plus separate static-layer provenance.

Current vehicle mechanics remain a useful browser/control specimen with explicit provisional or reference-only surfaces: `legacy_ts_m6`, drivetrain semantic mismatch, procedural wishbones, mixed FL/FR steering, provisional rack mapping and legacy split-wheel contact.

### Gate 3 — Owner truth + negative knowledge

Protected current product truth includes both Owner-facing steering modes, absolute-position pedals, multitouch/fail-closed input behavior, D/R pointer lifecycle, camera/fullscreen, accepted mobile composition foundation, accepted worlds and A53/Chrome render-1x scan boundary.

Current Owner-visible quality pressure clusters around:

- steering mechanics / return / contact quality;
- longitudinal power/brake balance;
- rig / visual-mechanical coherence;
- exact outboard mating, which remains not fairly Owner-judged.

Negative knowledge includes relative-from-touch pedals as superseded, click-only D/R acquisition as failed, Pedal Contact V1/V1.1 as not accepted/deferred, unsafe JURE inspect/edit coupling as rejected workflow behavior, stale visual ownership as non-authority and artificial rack centering as an unacceptable silent default substitute.

### Gate 4 — future-vision pressure

Future ambition is a falsifier of premature coupling, not an equal-priority requirements list.

Earned broadly reusable principles are authority/separation principles: relation-local ownership, authored/runtime separation, coherent replacement, provenance/deterministic identity, representation independence, world/vehicle separation and browser timing/input/presentation discipline.

Healthy domain specialization is explicitly allowed. Suspension, steering mechanics, drivetrain and tire/contact may remain wheeled-vehicle-specific. Flight dynamics may remain a future domain. Photogrammetry streaming/LOD/import belongs to the world/content domain. Advanced authoring UX may remain mechanism-specific.

Rejected premature commitments include universalizing current M6 topology, current JURE/Web schemas, one-authored-element=one-runtime-body, generic physics-plugin infrastructure without a second real backend need, shared tire/rotor dynamics, renderer/world-streaming redesign driven only by future ambition, mandatory JURE and a forced one-app/multi-app split.

## 2. Decision vocabulary

- `PRESERVE BEHAVIOR` — current product behavior has scoped Owner evidence; preserve against unrelated regression without freezing implementation.
- `INHERIT REQUIREMENT` — a property is strong enough to constrain the first relevant future design even if implementation changes.
- `INHERIT SEMANTIC` — preserve mechanical/authority meaning, not donor code/schema/constants.
- `INHERIT PRODUCT DIRECTION` — preserve current Owner-selected direction while requiring later challenge before final architecture.
- `EXTRACT TECHNIQUE` — current implementation contains a proven useful technique but is not itself architectural authority.
- `REIMPLEMENT` — current implementation is useful as evidence/control but should not define the future solution when that surface is selected.
- `RESEARCH` — evidence is insufficient for a durable solution; keep the question explicit.
- `REJECT` — do not inherit the claim as product/mechanical truth.
- `CONTROL` — preserve as comparison/falsifier/history, not target architecture.
- `IRRELEVANT-HISTORY` — keep in Git/history only; do not route current work through it.
- `OPEN / OWNER JUDGEMENT` — machine/source evidence exists but required qualitative/physical Owner truth is still missing.

Evidence-strength vocabulary is qualitative rather than numeric:

- `HIGH — CROSS-CORROBORATED`
- `HIGH — SCOPED OWNER`
- `HIGH — EXECUTED TECHNICAL`
- `MEDIUM — SOURCE/CONTROL`
- `REFERENCE / HISTORICAL`
- `OPEN / NOT FAIRLY JUDGED`

## 4. Gate 5 synthesis by disposition

### 4.1 Preserve current product behavior

Strong current Web stability capital:

- both Owner-facing steering interaction modes;
- absolute-position pedals with immediate pointer-down/frozen acquisition geometry;
- independent analog ownership, steering+pedal multitouch, D/R explicit pointer lifecycle and fail-closed lifecycle behavior;
- Camera Manual Rig V1;
- Fullscreen V1;
- current lower-driving/minimal-HUD/utility-drawer mobile foundation;
- accepted world capability including current JSPREV2;
- A53/Chrome render-1x scan boundary within its scoped evidence;
- exact-source Preview and separate static-layer provenance.

`PRESERVE BEHAVIOR` does not mean preserve exact DOM, CSS, classes, renderer, backend or future product layout forever.

### 4.2 Earned general constraints

The strongest cross-domain constraints are deliberately few:

1. explicit provenance and deterministic identity;
2. independent relation-local endpoint ownership;
3. authored truth separate from runtime dynamics/contact/solver and from runtime body granularity;
4. coherent-unit replacement rather than mixed incompatible geometry authorities;
5. visual representation must not silently become mechanical authority;
6. fail-closed interpretation where units/basis/provenance/ownership are ambiguous;
7. world/content semantics remain separable from vehicle mechanics;
8. browser simulation/input/presentation timing and observability remain explicit enough to falsify regressions.

These constraints would still be justified if drone/large-world ambitions disappeared. That is why they survive Gate 4.

### 4.3 Healthy wheeled-vehicle specialization

Do not universalize these merely because JV may later contain other machines:

- M6/double-wishbone topology;
- caster/KPI/back-drive steering mechanics;
- rack/tie-rod/full-lock geometry;
- suspension/ARB behavior;
- drivetrain torque/brake semantics;
- tire/contact architecture and its anti-centering falsifiers.

A later drone/flight case may share only lower-level authority/timing/provenance principles while keeping dynamics specialized.

### 4.4 Controls and negative knowledge

Keep comparison value without allowing old implementations to become targets:

- procedural wishbone geometry;
- FL source-registered/extra-carrier repair bridge;
- temporary symmetric FR steering;
- provisional rack normalization;
- split sphere+sidewall contact;
- historical wheel shapes;
- historical `5b92e9c` feel/tuning;
- current `legacy_ts_m6` backend;
- current R3 visual calibration;
- relative-from-touch pedals and historical X-position steering;
- rejected Pedal Contact V1/V1.1 approach.

The failure reason matters as much as the rejected status.

### 4.5 Explicit open decisions

Cheap to keep open now and therefore deliberately **not frozen**:

- TypeScript vs WASM/native-derived runtime;
- final renderer;
- final authoring application;
- JURE -> Web lowering/consumer architecture;
- serialized schema/component ontology/granularity;
- one app vs cooperating tools;
- backend/plugin architecture;
- world streaming/partitioning/LOD architecture;
- final tire architecture;
- exact runtime body/collider granularity.

Exact outboard mating is a conditional open item: cheap to keep open through Gate 6, but potentially blocking if a selected front-mechanics falsifier requires it.

## 5. Adversarial downgrade review

The strongest `PRESERVE` / `INHERIT` claims were challenged against their best downgrade arguments.

### Relation-local ownership

Strongest downgrade argument: it may be overfitted to wishbone authoring.

Verdict: **survives**. Independent endpoint ownership is corroborated by JURE and physical Native relation behavior, and it is a general relational-mechanism concept rather than an M6 topology claim.

### Authored/runtime separation
